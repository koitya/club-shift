# レビュー結果と変更点

旧版（Netlify＋Supabase・ChatGPT作成）をレビューして、仕組みから作り直しました。

## 旧版の問題点（重大な順）

### 仕組みの問題
1. **割り当てが不公平**：「全員の第1希望 → 全員の第2希望…」の順で処理していたので、第1希望が通ったバンドが第2希望でもう1枠取れる一方、負けたバンドは何ももらえないことがあった。候補を多く出すバンドほど有利だった
2. **過去の利用回数が永遠に累積**：古いバンドと新しいバンドの差が開き続ける。バンドを削除すると履歴ごと消える
3. **締切の仕組みがない**：確定後でも希望を書き換えられた。提出状況もわからなかった
4. **確定後に1枠だけ直せない**：月全体を再抽選するしかなかった
5. **運用の継続性**：Supabaseの無料プランは7日間アクセスがないと停止し、バックアップもない。復旧や管理者交代にはSQLの操作が必要だった

### バグ・セキュリティ
6. GitHub Pages（サブフォルダ公開）で動かない絶対パス
7. 登録処理が2段階で、途中で失敗すると「ログインできるのにバンドがない」アカウントが残る
8. 日本語の長いバンド名だと、内部のメールアドレスが長すぎて登録できない可能性
9. 希望の更新が「削除 → 追加」の2回の通信で、途中で失敗すると希望が消える
10. 過去の履歴の取得が1000件で打ち切られ、運用1年ほどで公平性が狂う
11. 誰でも登録できた（部外者対策がない）
12. 一括確定時に「同じ日2枠」「希望外の枠」をサーバー側でチェックしていなかった
13. 利用可否が未設定の日がカレンダーで「空き」と表示された
14. 統計の「登録バンド：全登録」が仮の文字のまま、同点時のランダムが偏る方式、説明文とアルゴリズムの不一致、ライブラリのバージョン未固定、など

## 新しい構成

| | 旧版 | 新版 |
|---|---|---|
| 画面の公開 | Netlify | GitHub Pages（GitHubだけで完結） |
| データ | Supabase（PostgreSQL） | Googleスプレッドシート |
| 処理 | ブラウザ＋SQL関数 | Apps Script（全部サーバー側） |
| 管理者 | バンド登録してからSQLで権限変更 | 管理者パスワードでログイン |
| 停止 | 7日アクセスなしで停止 | 停止しない |
| バックアップ | なし | スプレッドシートの変更履歴 |

## 維持した仕様
バンド単位のアカウント（バンド名＋8文字以上のパスワード、名前は一意、掛け持ちは別アカウント）／順位つきの複数希望・何度でも更新可／1日2枠・時刻は管理者が設定／枠ごとの利用可否／1枠1バンド／希望順位と過去の回数を考慮した公平な自動割り当て・同点はランダム・同じ日に2枠なし・希望外は割り当てない／プレビュー → 一括確定／確定シフトはログインした全員が閲覧／他バンドの希望は非公開

## 追加・変更した点
- 月ごとの状態（準備中・受付中・締切・確定）と、締切日時での自動締め切り
- 提出状況の一覧
- ドラフト方式の割り当て、過去の回数は直近N か月（初期値3）
- 仮割り当ての保存、手動変更、確定後の1枠変更、確定の取り消し
- 部の合言葉、ログイン失敗5回で10分ロック
- 管理者によるパスワードリセット・名前変更・停止、バンド自身のパスワード変更
- 時刻を月ごとに保存（過去の月の表示が変わらない）
- 操作ログ
- スマホ向けの画面（曜日つきの日付リスト、タップで希望を選ぶ、未保存の警告、次の練習の表示）

## 確認できていること・いないこと
- ✅ Apps Scriptの動きを再現した模擬環境で、サーバー側のテストを81項目実施（登録・ログイン・権限・希望・締切・割り当て・確定・取り消し・パスワード変更など）
- ✅ 割り当てアルゴリズムをランダムな2000パターンで検証（ルール違反0件。旧方式より0枠のバンドが減ることを確認）
- ✅ 実ブラウザ（スマホサイズ）で、登録 → 希望提出 → 割り当て → 確定 → 閲覧の一連の流れを確認
- ⚠ **本物のGoogle Apps Script上ではまだ動かしていません**。セットアップ後に[テストチェックリスト](テストチェックリスト.md)で確認してください
